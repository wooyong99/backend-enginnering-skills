# 유비쿼터스 언어 정의 가이드

## 유비쿼터스 언어란?

**정의**: 도메인 전문가와 개발팀이 공유하는 공통 언어

**목적**:
- 의사소통 오류 제거
- 코드와 비즈니스의 일치
- 도메인 지식의 명시화

**원칙**:
```
1. 비즈니스 용어를 그대로 코드에 반영
2. 모호한 용어는 명확히 정의
3. 기술 용어 사용 금지
4. 문서와 코드의 언어 일치
```

---

## 용어 발굴 프로세스

### 1단계: 비즈니스 대화에서 명사 추출

**방법**:
- 도메인 전문가의 설명 경청
- 반복적으로 나오는 용어 기록
- 핵심 개념 식별

**예시**:
```
도메인 전문가의 설명:
"고객이 주문을 하면, 우리는 결제를 승인하고,
재고를 확인한 후 배송을 시작합니다.
만약 재고가 없으면 주문을 보류하고 고객에게 알립니다."

추출된 명사:
- 고객 (Customer)
- 주문 (Order)
- 결제 (Payment)
- 재고 (Inventory)
- 배송 (Delivery)
```

### 2단계: 동사와 행위 식별

**방법**:
- 비즈니스 프로세스의 액션 파악
- 상태 변경을 일으키는 행위 식별
- 수동태보다 능동태 선호

**예시**:
```
비즈니스 행위:
- 주문을 하다 → place()
- 결제를 승인하다 → approve()
- 배송을 시작하다 → ship()
- 주문을 보류하다 → hold()
- 고객에게 알리다 → notify()
```

### 3단계: 용어 정의 및 합의

**문서화 형식**:
```markdown
## 용어: [이름]

**정의**:
명확하고 간결한 정의

**사용 맥락**:
어떤 상황에서 사용되는가

**관련 용어**:
- 유사 용어: [설명]
- 반대 용어: [설명]

**예시**:
- "고객이 주문을 생성한다"
- "시스템이 주문을 검증한다"

**코드 매핑**:
- 클래스: Order
- 메서드: place(), cancel()
```

### 4단계: 팀 전체 공유 및 검증

**검증 방법**:
- 도메인 전문가 리뷰
- 개발팀 코드 리뷰
- 정기적 용어집 업데이트

## 용어 분류

### 엔티티 후보 (Entity Candidates)

**특징**:
- 고유 식별자 필요
- 생명주기 존재
- 시간에 따라 변함

**식별 질문**:
```
1. 고유하게 식별되어야 하는가?
2. 다른 것과 구별되어야 하는가?
3. 추적이 필요한가?
4. 상태가 변하는가?
```

**예시**:
```
User (사용자)
- 식별자: userId
- 생명주기: 가입 → 활동 → 탈퇴
- 추적: 로그인 이력, 구매 이력

Order (주문)
- 식별자: orderId
- 생명주기: 생성 → 결제 → 배송 → 완료
- 추적: 상태 변경 이력

Product (상품)
- 식별자: productId
- 생명주기: 등록 → 판매 → 품절 → 단종
- 추적: 재고 변동
```

### 값 객체 후보 (Value Object Candidates)

**특징**:
- 속성으로만 식별
- 불변
- 측정, 수량, 설명

**식별 질문**:
```
1. 값으로만 비교되는가?
2. 불변인가?
3. 교체 가능한가?
4. 개념적 전체를 나타내는가?
```

**예시**:
```
Money (금액)
- 속성: amount, currency
- 불변: 변경 시 새 인스턴스
- 비교: 값이 같으면 같은 것

Address (주소)
- 속성: street, city, zipCode
- 불변: 주소 변경 = 새 주소 할당
- 개념: 주소는 하나의 완전한 개념

Email (이메일)
- 속성: value
- 불변: 변경 불가
- 검증: 형식 검증 포함
```

### 도메인 서비스 후보

**특징**:
- 여러 엔티티 조합 로직
- 엔티티에 속하지 않는 행위
- Stateless

**식별 질문**:
```
1. 어느 엔티티에도 자연스럽게 속하지 않는가?
2. 여러 엔티티를 조합하는가?
3. 순수한 계산이나 정책인가?
```

**예시**:
```
PriceCalculator (가격 계산기)
- 이유: Order, Coupon, MemberGrade 조합
- 책임: 최종 가격 계산

TransferService (이체 서비스)
- 이유: 두 Account 간 상호작용
- 책임: 이체 로직 수행

RefundPolicy (환불 정책)
- 이유: 복잡한 환불 규칙
- 책임: 환불 가능 여부 및 금액 계산
```

### 이벤트 후보

**특징**:
- 과거형 동사
- 비즈니스적으로 의미 있는 상태 변화
- 다른 컨텍스트에 알림 필요

**식별 질문**:
```
1. "~가 발생했다"로 표현되는가?
2. 다른 부분에 영향을 주는가?
3. 기록이 필요한가?
```

**예시**:
```
OrderPlaced (주문 완료됨)
- 시점: 주문 확정 시
- 영향: 재고 차감, 결제 시작

PaymentCompleted (결제 완료됨)
- 시점: 결제 승인 시
- 영향: 주문 상태 변경, 배송 시작

UserRegistered (사용자 가입됨)
- 시점: 회원가입 완료 시
- 영향: 환영 이메일, 초기 포인트 지급
```

## 동사 매핑 패턴

### 비즈니스 행위 → 도메인 메서드

**패턴 1: 상태 전이 동사**
```
비즈니스 용어        도메인 메서드         설명
-------------------------------------------------------
생성하다            create()            새 인스턴스 생성
등록하다            register()          시스템에 등록
시작하다            start()             프로세스 시작
완료하다            complete()          프로세스 완료
취소하다            cancel()            작업 취소
승인하다            approve()           승인 처리
거부하다            reject()            거부 처리
활성화하다          activate()          활성 상태로 전환
비활성화하다        deactivate()        비활성 상태로 전환
만료하다            expire()            유효기간 종료
```

**패턴 2: 비즈니스 액션 동사**
```
비즈니스 용어        도메인 메서드         설명
-------------------------------------------------------
주문하다            place()             주문 생성 및 확정
결제하다            pay()               결제 수행
배송하다            ship()              배송 시작
환불하다            refund()            환불 처리
적립하다            accumulate()        포인트 적립
사용하다            use()               포인트 사용
발급하다            issue()             쿠폰 발급
적용하다            apply()             할인 적용
```

**패턴 3: 검증/계산 동사**
```
비즈니스 용어        도메인 메서드         설명
-------------------------------------------------------
확인하다            verify()            검증 수행
계산하다            calculate()         값 계산
검증하다            validate()          유효성 검사
평가하다            evaluate()          조건 평가
비교하다            compare()           값 비교
```

### 금지 용어

**기술 중심 용어 (사용 금지)**:
```
❌ updateStatus()      → ✅ approve(), reject()
❌ changeState()       → ✅ activate(), complete()
❌ setData()           → ✅ register(), record()
❌ modifyValue()       → ✅ 구체적 비즈니스 동사
❌ processRequest()    → ✅ place(), pay(), ship()
❌ handleEvent()       → ✅ notify(), record()
```

**모호한 용어 (명확히 정의)**:
```
❌ "처리하다" (process)
   - 너무 포괄적, 구체적 의미 불명확
   ✅ 대신: approve(), validate(), execute()

❌ "관리하다" (manage)
   - 의미 불분명
   ✅ 대신: create(), update(), delete() 또는
           구체적 비즈니스 동사

❌ "수행하다" (execute)
   - 일반적, 비즈니스 의미 없음
   ✅ 대신: place(), ship(), refund()
```

## 실전 예시

### E-Commerce 도메인

```markdown
## 주문 (Order)

**영문**: Order

**정의**:
고객이 상품을 구매하기 위해 생성한 거래 단위.
결제부터 배송까지의 전체 생명주기를 관리한다.

**타입**: Entity (Aggregate Root)

**속성**:
- orderId: 주문 고유 식별자
- userId: 주문한 고객 ID
- items: 주문 항목 목록
- totalAmount: 총 주문 금액
- status: 주문 상태
- placedAt: 주문 확정 시각

**행위**:
- `place()`: 주문을 확정하고 결제 프로세스 시작
- `pay()`: 결제 완료 처리
- `cancel()`: 주문 취소
- `ship()`: 배송 시작
- `complete()`: 주문 완료 처리
- `refund()`: 환불 처리

**상태 전이**:
```
DRAFT → PLACED → PAID → SHIPPED → DELIVERED → COMPLETED
          ↓
       CANCELLED
```

**비즈니스 규칙**:
- 주문 금액은 0보다 커야 함
- PLACED 상태에서만 결제 가능
- SHIPPED 이후에는 취소 불가
- 환불은 DELIVERED 후 7일 이내만 가능

**사용 예시**:
- "고객이 주문을 **생성**한다"
- "고객이 주문을 **확정**한다"
- "시스템이 주문을 **결제 처리**한다"
- "관리자가 주문을 **배송 시작**한다"

**관련 용어**:
- OrderItem: 주문의 개별 상품 항목
- Payment: 주문에 대한 결제 정보
- Delivery: 주문의 배송 정보

**코드 위치**:
- Package: `com.shop.order.domain`
- Class: `Order.java`
```

## 용어집 유지보수

### 업데이트 시점

1. **새 요구사항 발견 시**
   - 새로운 비즈니스 개념 추가
   - 기존 용어 재정의

2. **코드 리뷰 시**
   - 코드와 용어집 일치 확인
   - 불일치 발견 시 즉시 수정

3. **도메인 전문가 미팅 후**
   - 새로 발견한 비즈니스 규칙 반영
   - 용어 정의 명확화

4. **정기 리뷰** (월 1회 권장)
   - 사용되지 않는 용어 제거
   - 모호한 정의 개선

### 용어 충돌 해결

**문제**: 같은 단어, 다른 의미
```
예: "Payment"
- 결제 컨텍스트: 결제 행위와 상태
- 정산 컨텍스트: 판매자에게 지급할 금액
```

**해결책**:
```
1. 컨텍스트별 분리
   - Payment (결제 컨텍스트)
   - Settlement (정산 컨텍스트)

2. 한정어 추가
   - CustomerPayment (고객 결제)
   - SellerSettlement (판매자 정산)

3. 명확한 문서화
   - 각 컨텍스트의 용어집에 명시
   - 컨텍스트 맵에 표시
```

### 팀 공유 방법

1. **Wiki/Confluence**
   - 검색 가능한 용어집
   - 버전 관리

2. **코드 주석**
   - 주요 도메인 클래스에 용어 정의 포함
   - JavaDoc/KDoc에 비즈니스 의미 명시

3. **정기 세션**
   - 도메인 학습 세션
   - 신규 멤버 온보딩

4. **용어 변경 공지**
   - 슬랙/메신저로 즉시 공유
   - 변경 이유와 영향 범위 명시
